# Strategic Focus Rule

## Why this rule exists

This project is vulnerable to two opposite mistakes:

1. **Strategic drift:** changing the course because a new tool, promotion, free credit, deadline, or exciting idea appears.
2. **Strategic inertia:** protecting the existing plan even when stronger evidence shows that another route would serve the learner and Dutch small and medium-sized enterprise (SME) clients better.

This rule prevents both. Opportunities are evaluated; they do not automatically become work.

## Main goal

Build the safest, most durable, market-relevant path from a literal beginner to a Controlled AI Workflow Implementation Consultant for Dutch small and medium-sized enterprises (SMEs), using evidence-backed capability gates and controlled implementations in the systems clients actually use.

Durable capability means being able to:

- discover and define a real business problem;
- map a process and its risks;
- choose proportionate controls;
- evaluate existing and proposed systems;
- build and test a bounded workflow;
- keep evidence, traceability, privacy, security, costs, and human accountability visible;
- support adoption and measure whether the implementation helped;
- transfer the method to another platform or work area.

## Core rule

**Do not let a temporary opportunity choose the curriculum, platform, sequence, or business direction.**

Tool expertise is useful only when it develops or proves a capability that advances the main goal at the right time.

## Mandatory strategic-fit gate

Answer these questions before any material addition or change:

1. **Goal contribution:** Which durable consulting capability does this improve or prove?
2. **Correct sequence:** Is this the best next step for a literal beginner, or does it skip prerequisites?
3. **Problem before tool:** Is there a defined client problem and use case before a provider or product is chosen?
4. **Evidence:** What current market, client, technical, safety, or learning evidence supports the change?
5. **Opportunity cost:** What higher-value work will be delayed or removed?
6. **Portability and exit:** What remains useful if the provider, model, price, credit, or product changes?
7. **Duplication:** Does the course already teach or prove the same capability?
8. **Simpler route:** Is there a cheaper, safer, simpler, or more representative way to achieve the learning outcome?
9. **Safety and authority:** Would this require paid billing, sensitive data, production access, external commitments, or authority the user has not provided?

Then classify the proposal:

### `STRATEGIC FIT: PASS`

Use only when the proposal clearly advances the main goal now, fits the sequence, has a defined learning or client outcome, and its opportunity cost is acceptable. Implement the smallest version that proves the outcome.

### `STRATEGIC FIT: PAUSE`

Use when the proposal may be valuable but is premature, weakly evidenced, duplicative, or dependent on a missing prerequisite or user decision. Put it in the idea backlog with a concrete trigger for reconsideration. Do not implement it now.

### `STRATEGIC FIT: REJECT`

Use when the proposal mainly consumes time or money, follows novelty or provider incentives, creates disproportionate lock-in or risk, or does not materially improve the path to the main goal. Explain why and remove it from the active plan.

## Automatic pause or rejection signals

Pause or reject by default when the main justification is:

- “the credits expire” or “it is free right now”;
- “we already spent time on it”;
- “this provider is popular” before the client problem is defined;
- a shortcut that skips current capability gates;
- a market claim without evidence from prospective clients;
- another demo that proves no new capability;
- provider lock-in or maintenance burden without a client reason;
- artificial intelligence novelty replacing process, controls, evidence, or human accountability;
- language that overstates beginner, consultant, production, security, compliance, or market readiness;
- a complex technical build when a simpler method proves the same outcome.

Free credits may reduce the cost of an already justified experiment. They cannot make an unjustified experiment strategically useful.

## Explicit goal-change procedure

The main goal can be refined or replaced, but never silently.

Before changing it, create a short decision record containing:

1. the current goal and proposed goal;
2. the problem the proposed goal solves better;
3. evidence for and against the change;
4. comparison of learner fit, Dutch market value, time, cost, safety, durability, reversibility, and opportunity cost;
5. the effect on existing courses, capstones, deployment, and planned work;
6. the strongest case for keeping the current goal;
7. a recommendation: `KEEP`, `REFINE`, or `REPLACE`;
8. the user's explicit approval or rejection.

Only after explicit approval may the main goal, career sequence, curriculum, and validation rules be updated together.

## Platform-selection order

For every client case, use this order:

1. understand the business problem, process, users, risks, evidence needs, and success measure;
2. inspect the systems the client already uses and their native capabilities;
3. consider a maintainable cross-platform automation or orchestration layer;
4. use custom code or cloud services only when the expected value and control needs justify the added complexity.

The Google Cloud controlled-document capstone is one bounded reference implementation. Promotional Google Cloud credit does not make Google the program-wide default. The consulting method must remain transferable to Microsoft, Google, specialist software, low-code tools, and other suitable stacks.
